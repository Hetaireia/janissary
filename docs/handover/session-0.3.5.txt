Rule 1 (amended, pending execution at session open next window)
---------------------------------------------------------------
Previous Rule 1 (session-0.3) required 5 steps at commit time:
  ruff check --fix . ; ruff format . ; ruff check . ;
  ruff format --check . ; pytest -q

Amended Rule 1:
  - ruff steps run at COMMIT via pre-commit framework (already in place).
  - pytest runs at PRE-PUSH via a separate hook (to be configured).
  - Coverage is whole-tree in both cases. No scope reduction.
  - The pre-commit framework is the mechanism; the git hook file is the
    entry point. Both are repository-versioned.

Reason for amendment:
  pytest in the pre-commit hook makes commits take >2 minutes on this
  machine (sh.exe residual from the pre-commit wrapper never exits cleanly;
  observed this session as a 120s+ hang on `git commit`). That is untenable
  and would be bypassed by any developer in a hurry — including this
  assistant. The amendment preserves Rule 1's intent (nothing ships
  without the gate) while removing the frequency mismatch (pytest belongs
  at push, not commit).

ENVIRONMENT GOTCHAS
=============================================================================

Building on session-0.3 §Environment gotchas. Unchanged items omitted here;
refer to session-0.3.txt for the full list. New items this session:

A. pre-commit `repo:` hooks are unusable on this network.
   GitHub HTTPS clone of astral-sh/ruff-pre-commit triggers a submodule
   update --init --recursive that can hang for HOURS. Symptom:
   `pre-commit run --all-files` sits on "Initializing environment for
   https://github.com/..." with no progress. Observed 2026-10-26 PM:
   submodule update processes (git 5348, git 16024, sh 16100) stuck from
   09:21 to 20:40, holding a lock on the cache directory (WinError 32).
   Fix: local-only hooks (done this session). Do not restore repo: hooks
   until the network permits GitHub clone or repos are mirrored.

B. pytest in pre-commit hook takes >2 minutes.
   Symptom: `git commit` hangs; git processes persist after timeout;
   residual sh.exe from the pre-commit wrapper never exits. The hook is
   functionally correct — the gate does run and does catch defects — but
   the timing makes it untenable. Fix: Rule 1 amendment (decided,
   executes next session).

C. Zombie git processes accumulate on this machine.
   Observed: a 22-hour `git for-each-ref --sort -committerdate` from the
   VS Code git extension (PID 13552) was holding our repo lock. It blocked
   our first attempt to clear the pre-commit cache lock, then blocked the
   git log probe after we cleared the cache. Diagnostic: `Get-Process git`
   and inspect StartTime for stale entries. Fix: `Stop-Process -Id <pid>
   -Force`. This is a VS Code extension issue, not a repo bug. If it
   recurs frequently, disable or update the VS Code git extension.

D. PowerShell Start-Job with array args to native executables is fragile.
   Observed: `git --no-pager log --oneline -6` passed via
   `Start-Job -ArgumentList @(...)` came back as the git usage message
   instead of the log. The arg array was mangled by the job runner. Use
   direct invocation for anything critical; Start-Job for diagnostics only,
   and verify the output is what you expected (a "usage:" prefix in log
   output is the tell).

E. CRLF warning on Add-Content writes to .txt handover files.
   Observed: "warning: in the working copy of 'docs/handover/session-
   0.3.txt', CRLF will be replaced by LF the next time Git touches it".
   Cosmetic. Git normalizes on next operation. No action needed.

F. `gh run view` does not accept `--branch`.
   The flag exists on `gh run list`, not on `gh run view`. Query by
   run-id, or filter `gh run list --json headSha,...` output.

G. `gh run view <run-id>` — angle brackets are documentation placeholders,
   not literal. PowerShell interprets `<` as redirection and errors with
   "The '<' operator is reserved for future use." Always substitute a
   real numeric run-id.

H. `gh run list --json ...` returns a JSON string, not an object.
   Must `| ConvertFrom-Json` before `Where-Object` can filter on fields.
   Canonical pattern for "is my SHA green?":

     gh run list --branch main --limit 5 `
         --json headSha,conclusion,workflowName,databaseId |
       ConvertFrom-Json |
       Where-Object { $_.headSha -like "<sha-prefix>*" }

   This is the most reliable CI status check post-push (Rule 3).

I. Multi-hour cache locks on Windows require process-level attribution
   before cleanup. The pre-commit WinError 32 (this session) was resolved
   by identifying specific orphaned PIDs (git 5348, git 16024, sh 16100)
   and killing them individually. Blanket `Stop-Process -Name git` risks
   collateral damage to unrelated git operations. Always attribute first,
   then kill specific PIDs.

J. ruff-format can crash with STATUS_ACCESS_VIOLATION on Windows.
   Observed during a push-stage pre-commit run (before the Rule 1
   amendment took): `ruff format .` exited 3221225501 = 0xC0000005 =
   STATUS_ACCESS_VIOLATION. The very next hook in the same run
   (`ruff format --check`) passed, and full pytest passed. Transient
   binary crash, not a formatting failure. Retry once; if it recurs
   consistently, investigate the ruff install (version, wheel arch,
   antivirus interference).
