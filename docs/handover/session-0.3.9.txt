WHAT THIS SESSION DELIVERED, IN ONE PARAGRAPH
=============================================================================

Session 0.3.9 opened with a stale label and closed with a shipped
feature. The "401 abort - Phase 1.1 -> 1.2, open" item had been
carried in the known-issues table for at least three sessions. A
two-pass recon proved it described no defect: the scanner has no
abort path, no Phase 1.1/1.2 references exist in the tree, the
recon-layer 401/403 handlers are correct and tested, and auth session
propagation from cmd_scan through Scanner._request works end-to-end.
But the label pointed in a real direction. The static-v1 auth
docstring names the actual concern: "a token that expires mid-scan
will produce a run of 401s and that's a documented limitation." A
run of 401s means the injection engine evaluates login-page bodies
against injection signatures, correctly concludes "not vulnerable"
because there is nothing to match, and reports a clean scan against
a target the scanner was locked out of. Silent false negatives. That
is an enterprise-parity gap of the same class ADR-009 closed for
SARIF - the tools JANISSARY competes with (Acunetix, Burp
Enterprise, Invicti) all detect session loss and abort or
re-authenticate. Session 0.3.9 shipped ADR-010 (design lock, 236
lines) and its implementation (194 insertions across scanner.py,
cli.py, test_scanner.py) across two commits. The detector is a
six-line insertion in the payload loop: increment on 401, reset on
any non-401, fire when auth_configured and the counter reaches 2.
Abort sets summary.aborted and summary.abort_reason (naming the
counter, param, and last payload), breaks the loops, falls through
to post-loop grouping so partial findings are preserved, and exits
with code 2 - the pre-existing abort signal cmd_scan already
handles. Six new tests cover the threshold boundary, reset-on-
success, findings-preservation, default-False behavior, and the
exact abort timing. Test count 597 -> 603, F1=0.921 unchanged, CI
green on both commits. The session's second durable output is the
pattern: a stale label in the known-issues table is itself a signal
worth investigating. When a label says "deferred, phase X to Y,
open," and multiple sessions pass without anyone re-examining the
label against current code, the label has almost certainly drifted.
Retiring it honestly - "this describes no defect" - and then asking
"but what was the concern that motivated the label?" is the right
response. In 0.3.9 that path turned a 3-session-old dead row into a
shipped ADR. There are likely other labels in the table with the
same property. Session 0.3.10 opens at a stale-label sweep of the
remaining known-issues items; the sweep will either retire dead
labels or surface one or two more ADR-010-class concerns to scope
against real code.
