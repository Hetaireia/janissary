§11 — Phase 1.3d design decisions (unresolved)
1.3d implements the >20 collapse path from ADR-002 §Combined signal:
`distance > 20 AND auxiliary signal`. This is where baseline_struct
(1.3b, dead code) finally gets consumed.

1. Auxiliary signal sources. ADR-002 lists three: body length <10% of
   baseline, no `<` in body, known-file signature (e.g. /etc/passwd
   format). In scope for 1.3d - all three, or subset? Recommend all
   three, each gated separately.

2. Integration point in scanner.py. 1.3c established post-process-
   raw_findings as the pattern for admin. Same pattern for payload
   loop, or build a new oracle that fires on collapse + auxiliary?

3. baseline_struct consumption. compute_arming_state returns armed,
   reason, fingerprints, root_signature, sample_count, hamming_max.
   1.3d needs armed + fingerprints + root_signature. Does the API
   need to change?

4. New finding_type or reuse. ADR-002 says "confirm traversal or
   similar". Recommend a dedicated finding_type (e.g.
   traversal_collapse) mapping to pathtraver category, kept distinct
   from pathtraver_existence_oracle.

5. >20 threshold validation. ADR-002 verification plan notes a
   synthetic one-node fixture does not exercise collapse. 1.3d MUST
   have a real collapse fixture (/etc/passwd flat text vs a real
   HTML baseline) before merging.

6. Benchmark acceptance. Pathtraver F1 currently 0.049-0.308. Does
   1.3d aim for the pathtraver ceiling, or is that 2.2? Recommend
   1.3d = emit-only (recall on genuine collapse); 2.2 = payload
   coverage. Both required for the ceiling.

7. D5 pass-through contract for 1.3d. When armed=False or
   root_signature is None (ADR-004 D4), 1.3d must not emit. Contract
   = findings equal to pre-1.3d. Confirm scope extends to emit.

8. 1.3e boundary. Which tests go in 1.3d vs 1.3e? Recommend 1.3d
   ships unit + integration for emit; 1.3e ships void-tag fixture,
   swallowed-attribute fixture, and the 3-run F1 rerun.

Resolve all 8 before writing 1.3d code.
