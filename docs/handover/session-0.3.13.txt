PROCESS RULES - AMENDED
=============================================================================

Rules 1-14 unchanged from session-0.3.12.

AMENDMENT to Rule 13 (Rule 13b): git write operations require
post-operation verification with retry.

The prior Rule 13 said "git subprocess output is unstable; retry-on-
empty with cross-check" for informational commands. This session
proved that write operations have the same class of failure with a
worse failure mode: a `git add` call can return exit 0 while silently
staging nothing. The commit then fails with "nothing staged," which
looks like a build problem but is a git-subprocess problem.

Rule 13b: every git write operation (`add`, `commit`, `push`) is
followed by a read-back verification that checks the operation
actually took effect:

  git add <files>
  -> git diff --cached --name-only returns the expected set

  git commit ...
  -> git rev-parse --short HEAD differs from pre-commit HEAD
     (already in place since gotcha T)

  git push ...
  -> git rev-parse origin/main == git rev-parse HEAD
     (currently implicit; should be explicit)

Each read-back gets retry-on-empty with up to 3 attempts (Rule 13).
If the read-back fails after retries, throw with the count and the
missing set.

Implementation pattern: the git-add loop in this session's commit
block (attempt 1..3 with post-add staged-count check). It is the
template for Rule 13b going forward.
