NEW this session:
- ruff format . and ruff check . are DIFFERENT tools. Passing
  `ruff check <file>` does not imply `ruff format --check`
  will pass. Both must run on whole tree.
- ruff check --fix . must come BEFORE ruff format . — import
  sort and unused-import removal are check territory, not
  format territory. Reversed order means check failures
  survive the format step and stop the pipeline.
- CI runs 3 checks (ruff check ., ruff format --check .,
  pytest -q) in that order, whole tree, 5 Python versions.
  Any local gate that runs a subset is insufficient.
- gh run list --json with empty fields returns empty strings,
  not nulls. Check `-eq "success"` not `-ne ""`.
- `git ls-remote origin main` is a good push-transport
  diagnostic — it exercises network+auth for read without
  pushing. If it succeeds but push fails with `aborted
  session`, that's the credential helper holding state, not
  a network path issue.
- Push failures with `remote helper 'https' aborted session`
  recover on retry. Confirmed twice this session. One retry
  after 3s, then report — do not retry indefinitely.

§8 — Session lessons and locked process rules
Supersedes 1.3e §8. Prior lessons still apply, but these are
load-bearing now:

PROCESS RULE 1 (pre-commit gate): Before any commit that
touches src/, tests/, or docs/, run ALL THREE CI checks
verbatim on whole tree, in order:
    ruff check --fix .         # sort imports, remove unused
    ruff format .              # formatting
    ruff check .               # verify no lint remains
    ruff format --check .      # verify formatting
    pytest -q                  # tests
Any failure halts the pre-commit sequence. This is not
optional. The two red commits this session (fa58641,
354f843) were caused by skipping or shortcutting this rule.

PROCESS RULE 2 (pre-push gate): Before any push, verify the
PREVIOUS commit's CI is `conclusion: success`. Never push on
top of a red predecessor. `gh run list --branch main
--limit 1 --json status,conclusion` — if not success, fix
first.

PROCESS RULE 3 (post-push gate): After pushing, poll CI to
completion before starting new work. A push that "succeeded"
is not a green tree. If CI fails, diagnose before making
further changes.

PROCESS RULE 4 (control flow): Multi-step PowerShell scripts
MUST be wrapped in `& { ... }` with `return` inside. A `return`
at top-level of a bare script is a no-op — the script continues
after "STOP" and produces misleading green success messages.

PROCESS RULE 5 (heredoc discipline): Heredoc terminators must
be at column 0. `'@` inside `& { }` still needs to start the
line. Do not chain `'''` (Python triple-quote close) into the
same line as `'@` — PowerShell will not recognize it.

PROCESS RULE 6 (scope verification before commit): After the
pre-commit gate, run `git status --porcelain` and explicitly
verify that the file set matches intent. If any unexpected M
prefix appears on a non-target file, STOP. This catches drift
where ruff --fix touches something adjacent you didn't intend.

PROCESS RULE 7 (commit message form): Use repeated -m "..."
arguments, never heredoc $msg. Em dashes in commit subjects
can break PowerShell argument passing. Keep subjects under
72 chars.

PROCESS RULE 8 (transient push retry): On push failure with
"aborted session" / "RPC failed" / "Could not resolve host",
wait 3s and retry ONCE. If second attempt fails, report to
user — do not loop. Commit is safe locally; retry later.
