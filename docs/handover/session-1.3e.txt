§7 — Environment limitations (new this session)
Unchanged: pre-commit broken; PS7 no heredocs; code <newpath> opens
unsaved buffer; gh run view needs numeric ID; < reserved.

NEW: git commit -m $msg with heredoc $msg is fragile. Use repeated
-m "..." arguments or write $msg to a file outside the repo via
[System.IO.Path]::GetTempFileName(). Em dashes in subjects can break
argument passing.

NEW: Bare `git push origin main` (no output capture) can fail silently
with no error text in the terminal. Always capture: $out = git push
origin main 2>&1; print $out; check $LASTEXITCODE.

NEW: Set-Content does not halt sequence on failure inside & { }. A
throw must be followed by a loud ">>> STOP" line and any subsequent
paste must re-verify preconditions before acting.

NEW: `git status --porcelain` gives M / ?? / D prefixes with no
summary — critical for diagnosing "why didn't git add work".

NEW: $env:TEMP resolves to 8.3 short path that Remove-Item cannot
reach. Use [System.IO.Path]::GetTempFileName().

NEW: transient 0xc0000005 git crash in gh run view during CI poll
loop — cosmetic, next poll recovers.

NEW: file paths drift between sessions. test_dom_hash.py is at
tests/test_dom_hash.py, not tests/unit/. Always Test-Path before
assuming.

NEW: ResponseSnapshot has NO status_code field. Fields: status,
body, normalized, fingerprint, length, normalized_length, elapsed,
content_type. BaselineArmingState: armed, reason, fingerprints
(tuple of int), root_signature, sample_count, hamming_max.

§8 — Session lessons (prior all still apply)
NEW this session:
1. Heredoc -m $msg is fragile; use multi -m args.
2. Em dash in commit subject can break PS7 argument passing.
3. Prefer full-file rewrites (Set-Content) over surgical edits when
   the file is under 100 lines.
4. & { } wrapper is necessary but not sufficient: explicit pre-flight
   checks at start of every commit/push paste.
5. STOP markers must be loud, use Write-Host -ForegroundColor Red.
6. Line-count thresholds must be computed against expected length,
   not guessed above. Two "STOP" cycles this session were false
   positives from over-guessed thresholds (60 for a 54-line paste;
   220 for a 203-line handover).
7. Use `return` not `throw` inside & { } for non-fatal failure paths
   — throw exits the block but the terminal stays "failed"-looking;
   return leaves state visible for user.
8. When append-only passes a threshold, verify with
   Select-String -Pattern '^def test_' count, not just line count.
9. subprocess per-case harness (benchmark/track_a/runner.py) means
   payload changes in scanner.py DEFAULT_PAYLOADS flow to benchmark
   without harness edits.

§11 — Phase 0.3 scope discovery (unresolved — to be investigated)
Phase 0.3 is "stable finding fingerprint" per the 1.3b handover. It
has never been designed. This section lists the questions to answer
before proposing decisions.

1. What does "stable finding fingerprint" mean? Candidate: hash over
   (param, payload_family, finding_type, normalized_url, canonical_
   response_signature) such that the same vulnerability found twice
   across scans gets the same ID. If the existing
   src/janissary/detection/fingerprint.py already does this, 0.3 is
   an extension not a new build.
2. What is the current fingerprint strategy? Read
   detection/fingerprint.py + tests/unit/test_fingerprint.py.
3. What consumes fingerprints today? finding_store, grouping, agent
   adapters? Map the call sites.
4. What causes fingerprint instability across scans? Response body
   tokens that rotate (nonces, timestamps, IDs), random ports,
   session IDs in URLs. The "stable" part requires canonicalization.
5. Is the target duplicate-detection (same finding twice in one
   scan) or cross-scan identity (same finding across runs)? These
   are different requirements.
6. Does 0.3 interact with the enterprise roadmap? Reopening findings
   across scheduled scans, deduplication in dashboards, SARIF
   fingerprints for CI integration — these all need stable identity.
   If yes, 0.3 requirements come from Phase 6 design, not from a
   standalone spec.
7. Benchmark impact: 0.3 is expected to be metric-neutral (grouping
   already exists). Confirm no F1 regression risk.
8. Scope boundary: 0.3 ships the fingerprint scheme + tests. Does
   it also ship a migration for existing finding stores, or is that
   a follow-on?

Resolve these into concrete decisions in the next session's §11-style
list before any 0.3 code.
