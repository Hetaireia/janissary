## Question

## Investigation

Read ADR-027 in full at `docs/decisions/ADR-027-pathtraver-recall-strategy.md` (467 lines). The apparent ambiguity comes from reading only the ADR header, which says "D8 amended to dual-scope (see D8 AMENDED section)."

### What the ADR actually says

1. **D7 verification** (line 390): R = 0.075, below the D7 threshold of 0.15. This triggers literal D8 (candidate-only).
2. **D8 AMENDED 2026-11-05** (line 403): Path Z (dual scope) adopted instead of literal D8. The amendment is formal: DAST-APPLICABLE continues to include pathtraver (F1 0.922, ADR-001 stable); SUPPORTED-CLASSES excludes pathtraver (F1 0.978, reported alongside).
3. **D8 AMENDED — CORRECTION 2026-11-05** (line 440): A code defect in `score_dast_aware.py` made the benchmark gate check 0.977 instead of 0.922 for commits `7ab8083` through `ecec4fa`. Fixed in a follow-up commit. The dual-scope claim is now actually true.
4. **Status line** (line 438): "Accepted (2026-11-05). D8 amended as above; both metrics reported."

### What the code actually does

`src/janissary/engine/scanner.py` carries three ADR-027 references:
- Line 96: `# ADR-027 D3: broaden traversal payload coverage. Windows file` — the D3 payload additions (win.ini, encoded, double, dot).

The traversal oracle (`check_pathtraver_oracle` at `src/janissary/detection/analyzer.py:784`) continues to emit **findings** through the VerificationEngine, not candidates. This matches ADR-027 D8 AMENDED (Path Z), which keeps DAST-APPLICABLE scoring unchanged.

### What the surrounding documentation says

- `README.md` benchmark section: reports both DAST-APPLICABLE (0.922) and SUPPORTED-CLASSES (0.978) with the path traversal disclosure paragraph that names ADR-027 and states "excluded from the supplemental supported-classes score, as defined by ADR-027."
- `README.md` Known Limitations: "Path traversal: weak measured recall (0.075). Detection is implemented, but measured recall on the current corpus is low. Included in DAST-applicable and excluded from supported-classes."
- `docs/CAPABILITIES.md`: "Path traversal | Partial | Recall 0.075 at 7.11.1; per-category F1 0.049 / 0.154 / 0.160 / 0.308."

## Resolution

**No ambiguity remains.** ADR-027 D8 AMENDED is normative:

1. Path traversal detection is implemented as a verified finding pathway (not candidate-only).

2. DAST-APPLICABLE scoring includes pathtraver cases. DAST-APPLICABLE F1 remains 0.922.

3. SUPPORTED-CLASSES scoring excludes pathtraver cases. SUPPORTED-CLASSES F1 is 0.978.

4. Both metrics are reported side by side; neither is presented as "the" headline without the other.

5. Code, README, CAPABILITIES.md all conform to this decision.

D-17 is **resolved**, not because the code or ADR changed today, but because the code and ADR already agreed when read in full. The prior register entry preserved an ambiguity that was resolved on 2026-11-05.

## What D-17 was never about

The handover §4 describes D-17 as "diff ADR-027 against scanner.py IDOR path." That framing is incorrect:

- ADR-027 concerns **path traversal**, not IDOR.
- IDOR is governed by ADR-024 (candidate probe) and ADR-031 (public-resource suppression), both of which describe IDOR as candidate-only.
- The two subsystems are distinct: path traversal emits findings through the VerificationEngine; IDOR emits candidates outside the engine (per ADR-030 Rule 1).

If the D-17 resolution is to be tested against IDOR, that is a separate question — and both the code and the ADR-024/031 record already agree: IDOR is candidate-only.

## Forward-looking

No new ADR is required. No code change is required. The next time M37 (path traversal recall improvement) is scoped, ADR-027 D3-D5 remain the roadmap for cheap improvement; ADR-027 D8 AMENDED already anticipates a future candidate-only or scoring exclusion if D7 is retriggered. The current decision is not superseded by any subsequent ADR.
